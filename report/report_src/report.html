1. Task and what I did

The Group 9 topic is to detect vulnerable Java functions with CodeBERT and a class-weighted cross-entropy loss, as a partial reproduction of the study by Shestov et al. (2025). I did the whole project on my own. The task also asks to manage the data through its whole lifecycle and to show how governance, quality, integration, security and analytics affect the model. The report follows that order: one section for each lecture, then the model, the results, and what an organization should do with them.

The task table gives "CodeBERT + Class-Weighted Loss /" as the alternative method for Group 9, and the part after the slash is empty. I read it as the light version of the same idea: CodeBERT is frozen and only turns each function into a vector, and a small classifier is trained on these vectors with the same class weights. The primary method ran on my laptop without problems, so I did not have to switch. I ran the alternative anyway, because the project objective asks to compare the two on quality, cost and risk.

My research question comes from the paper. The authors write that plain class weighting did not work for their large model, so they moved on to focal loss and sample weights. I test whether class weighting helps CodeBERT, a model of the same family as ContraBERT, the smaller model the paper compares against, and what the answer means for an organization that wants to use such a model.

What I built:

  • a data pipeline that downloads the dataset at a fixed commit, checks it, cleans it and loads it into a SQLite warehouse that follows my ER model;
  • CodeBERT fine-tuned with class-weighted cross-entropy, two ablations (no weights, milder weights) and one run on the balanced version of the dataset;
  • the alternative method and three simple reference models;
  • an evaluation with 95% confidence intervals, charts and a live demo;
  • governance and security rules that the code enforces, not only describes.
Main results
  • CodeBERT with class-weighted cross-entropy reached a test ROC AUC of {{R_P_ROC}} and an F1 of {{R_P_F1}}, the same as the paper's CodeBERT-style baseline (0.85 and 0.22).
  • Class weighting did not help. The same model without weights was at least as good (ROC AUC {{R_PL_ROC}}, F1 {{R_PL_F1}}). The weights only move the decision threshold.
  • Accuracy depends on the threshold: {{R_P_ACC}} with the paper's rule, {{R_P_ACC05}} at 0.5. A model that flags nothing reaches {{R_MAJORITY_ACC}}, so the 93% target says little on this data.
  • No model can tell a vulnerable function from its own fixed version (ROC AUC about 0.5). The models learn which code a fix touched, and a simple TF-IDF model does as well as CodeBERT.
  • As a triage aid the model still helps: reading the top 10% of functions finds {{R_BUDGET_10}} of the vulnerable ones ({{R_PL_BUDGET_10}} without weights).

Usage policy

  1. Purpose. The data and the models are used only for this course, to study vulnerability detection.
  2. No redistribution. The source repository has no licence, so my submission does not contain the code samples. It pins the commit, and the pipeline downloads the files.
  3. A triage aid, never a gate. No code is called safe because the model did not flag it.
  4. No analysis of people. Commit ids lead to the developers who wrote the code. I never look up authors and never rank developers by their bugs.
  5. Labels are not edited by hand. Conflicting labels go to quarantine with the reason and wait for a security expert.
  6. No model without a record. Every model has a run summary with the data version, configuration, training time and SHA-256 of its weights. A model without one is not used.

Ethics and law

  • Labels are noisy. They come from a rule: the function before a fix is vulnerable, the same function after the fix is not. A fix can also change unrelated code, and a "fixed" function can still be vulnerable. Croft et al. (2023) found such errors in many vulnerability datasets. Even a perfect score would not mean a perfect detector.
  • Dual use. A model that finds vulnerabilities helps an attacker as much as a defender. I only use public vulnerabilities that were fixed long ago, and I treat any list of predicted vulnerable functions as restricted data (section 7).
  • False confidence. A model with 97% accuracy sounds safe to a manager. Section 9 shows why that number says almost nothing on this data.
  • Personal data. A commit hash is not a name, but it leads to the author's name and email in Git. Under GDPR and the Kazakhstan Law No. 94-V on personal data, that makes it indirectly identifying data. I keep commit ids only because the split depends on them, and I never fetch anything about the authors. If a company ran this model on its own code, the results would point at its own staff, and the Kazakh law would also require that this data stays on servers in Kazakhstan.

4. Data model (Lecture 3)

Figure 2, on the first landscape page after section 5, is the conceptual model. I built the warehouse straight from it: every entity is a table with the same keys, and SQLite enforces the foreign keys. The model has two parts, the data (blue) and the experiments (orange), and they meet only in prediction.

  • The label is stored once. The source files carry both target and status, but the status already decides the label: P1 (vulnerable) means 1, P2 (fixed) and P3 (unchanged) mean 0. Keeping both in the function table is a transitive dependency. It breaks third normal form and lets the two disagree. So the label lives in label_partition, and the view model_input joins it back for training.
  • A commit is an entity. The authors split the data by commit, and a commit links the vulnerable and the fixed version of a function. The {{D_COMMITS}} commit hashes come in 8 different lengths (Lab 3), so I never join on them across sources. I use a fingerprint of the code for that.
  • Business rules are constraints. A split is train, valid or test. A label is 0 or 1. A review status is clean, needs_expert_review or duplicate. A probability is between 0 and 1. A SHA-256 has 64 characters. The database refuses any row that breaks these rules.
  • Every row has lineage. source_file and source_line point to the exact line in the original JSONL file, and every change made to a row is in quality_issue.

6. Data quality (Lecture 5)

At first sight the data is clean: no missing values, every label is valid, every function parses as Java. The real problems are about meaning, not format. Table 3 lists my rules. I never change a label and never guess one. A row with a doubtful label goes to quarantine with its reason and stays in the warehouse for an expert.

{{T_RULES}}

Three results matter. {{D_CONFLICT_FUNCS}} functions have the label "vulnerable" in one version of the dataset and "not vulnerable" in the other, and 3 more rows have identical code with both labels. {{D_LEAK_ROWS}} rows in validation or test were copies of a function already in an earlier split, so a model would have been tested on code it had seen; I removed the later copy. And 659 functions had Windows line endings, which I changed to the usual Unix ones.

{{T_QUALITY}}

Class distribution

After cleaning, X1 with P3 has {{D_POS_WITH}} vulnerable functions out of {{D_CLEAN_WITH}}, about one in {{D_ONE_IN}}. The test split has only {{D_TEST_POS}} of them. This has two consequences. A model that always says "not vulnerable" is right {{R_MAJORITY_ACC}} of the time on the test split. And every recall or F1 on the test split rests on about a hundred cases, so I give confidence intervals. The balanced version (X1 without P3) has {{D_CLEAN_WITHOUT}} functions, about half of them vulnerable.

Length of the code

Vulnerable and fixed functions are long. Their median lengths are {{D_MED_P1}} and {{D_MED_P2}} tokens, and about half of them are longer than CodeBERT's limit of 512 tokens, so their end is cut off. The unchanged P3 functions have a median of only {{D_MED_P3}} tokens. This matters in two ways. The model may never see the line with the bug. And length alone separates P3 from P1 quite well, so a model can score high by learning that long code is risky. The length-only model in section 9 measures how far that gets.

8. Method and experiments

Primary method: CodeBERT with class-weighted cross-entropy

CodeBERT (Feng et al., 2020) is a RoBERTa encoder with 125 million parameters, pretrained on source code and its documentation. I put the standard classification head on top (a small two-layer network on the first token) and fine-tune all weights.

Plain cross-entropy treats every function the same. With one vulnerable function in {{D_ONE_IN}}, a model can keep the loss low by mostly saying "not vulnerable". Class-weighted cross-entropy multiplies the loss of each example by the weight of its class:

L = − Σi wyi log p(yi | xi) / Σi wyi,    wc = N / (2 Nc)

N is the number of training functions and Nc the number in class c. The training split has {{D_TRAIN_N}} functions, {{D_TRAIN_POS}} of them vulnerable, so the weights are {{W0}} for "not vulnerable" and {{W1}} for "vulnerable". One vulnerable function counts as much as {{W_RATIO}} others. The milder ablation uses the square root of these weights ({{W0S}} and {{W1S}}).

Protocol

I follow the protocol of the paper (appendix B): train for a fixed number of epochs, keep the checkpoint with the best ROC AUC on the validation split, choose the threshold that gives the best F1 on the validation split, and only then score the test split, once. The test split plays no part in any choice.

{{T_CONFIG}}

Alternative method and reference models

Alternative. CodeBERT is frozen. One pass over the data turns every function into a 768-number vector (the mean of CodeBERT's last layer over all tokens). A logistic regression with the same balanced class weights is trained on these vectors; its strength C is chosen on the validation split. Only {{ALT_PARAMS}} numbers are trained instead of {{PRIMARY_PARAMS}}.

Reference models. Three simple models show what the numbers mean. "Always not vulnerable" shows what accuracy is worth on this data. "Code length only" is a logistic regression on the length of the function and nothing else. "TF-IDF" is the class-weighted logistic regression on code tokens from Lab 4.

9.1 The test results

Table 7 shows every model on the test split of X1 with P3. The primary model reaches a ROC AUC of {{R_P_ROC}} (95% interval {{R_P_ROC_CI}}) and an F1 of {{R_P_F1}}. The paper reports 0.85 and 0.22 for ContraBERT, the CodeBERT-style model it compares against, so my partial reproduction lands on the same numbers.

{{T_METRICS}}

The surprise is the simple models. TF-IDF with a logistic regression, the Lab 4 baseline, reaches a ROC AUC of {{R_TF_ROC}}, and its F1 ({{R_TF_F1}}) and PR AUC are clearly better than CodeBERT's (Table 9). A model that sees nothing but the length of the code reaches {{R_LEN_ROC}}. On this benchmark, a transformer with 125 million parameters does not beat a bag of words. Section 9.4 shows why.

9.2 The accuracy target

The task asks for an accuracy of at least 93%. On this data the target says little, because the model that never flags anything reaches {{R_MAJORITY_ACC}}. What a real model reaches depends on its threshold, so Table 8 gives three operating points, each fixed before the test split was scored.

{{T_THRESHOLD}}

With the paper's rule (best F1 on validation) the model flags {{R_P_FLAG}} of the {{D_TEST_N}} test functions, and its accuracy is {{R_P_ACC}}, below the target. When I pick the threshold that gives 93% on validation instead, test accuracy is still only {{R_P_ACC_TARGET}}. The reason is a shift between the splits: at the same threshold the model flags {{R_VALID_FLAG}} of the validation functions but {{R_TEST_FLAG}} of the test functions, because the test commits come from other code. At the default threshold 0.5 the model flags {{R_P_FLAG05}} functions and reaches {{R_P_ACC05}}, so the target is met, but recall drops from {{R_P_REC}} to {{R_P_REC05}}.

The 93% target can be met, but only by flagging less. On this data accuracy mostly measures how few functions a model flags. For a security team the useful question is how many real vulnerabilities it finds for the review work it can afford (section 9.5).

9.3 Does class weighting help?

This was my research question, and the answer is no. Table 9 compares the two runs on the same 2,000 resamples of the test split. The model trained without weights ranks the functions at least as well: its ROC AUC is {{R_PL_ROC}} against {{R_P_ROC}}, and its PR AUC {{R_PL_PR}} against {{R_P_PR}}. Neither difference is clear, because both intervals include zero. Its F1 at the tuned threshold is clearly higher ({{R_PL_F1}} against {{R_P_F1}}), and it finds more vulnerable functions at every review budget (Table 10). It was also better on validation after every epoch (Figure 6).

What the weights do is move the scores. Without weights the model gives low scores to almost everything: at the default threshold 0.5 it flags only {{R_PL_FLAG05}} test functions. With weights it flags {{R_P_FLAG05}}. The paper's protocol picks the threshold on validation anyway, so this shift buys nothing; the plain model simply gets a lower threshold ({{R_PL_THR}} against {{R_P_THR}}). The weights also make the probabilities less honest: the plain model's validation log loss stays near 0.10, while the weighted one rises to 0.22 after the third epoch. The milder square-root weights ({{W0S}} and {{W1S}}) change nothing here: test ROC AUC {{R_SQ_ROC}} and F1 {{R_SQ_F1}}, with no clear difference from the full weights (Table 9). More weight never helped, and no weight did best.

Class weighting did not help CodeBERT, the same answer the paper gives for its large model. The weights act like a lower threshold built into training. Choosing the threshold on validation gives the same effect without retraining, and the model trained without weights was at least as good on every measure.

9.4 What the model actually learned

Figure 10 splits the test functions by partition. At its threshold the model flags {{R_FLAG_P1}} of the vulnerable functions and {{R_FLAG_P2}} of their fixed versions, but only {{R_FLAG_P3}} of the unchanged functions. On vulnerable functions against their own fixed versions its ROC AUC is {{R_P_P1P2}}, which is chance. TF-IDF and the length model are at chance there too (last column of Table 7).

So the model has learned to tell code that a fix commit touched from code that no fix touched. It has not learned what makes code vulnerable. This fits what section 6 found: unchanged functions are short, and a vulnerable function and its fix differ in a few tokens, often after the 512-token cut. Most of the high ROC AUC on X1 with P3 comes from the easy P3 negatives. The paper shows the same from the other side: on the balanced dataset, where every negative is a fixed function, its best model reaches only 0.69.

9.5 What a review team gets

A model like this is useful as a way to order work. If a team reads the top 5% of test functions by score ({{R_BUDGET_5_N}} functions), it finds {{R_BUDGET_5}} of the vulnerable ones. Reading 10% finds {{R_BUDGET_10}}, and reading 20% finds {{R_BUDGET_20}}. In random order the team would find 5%, 10% and 20%. TF-IDF does a little better at every budget (Table 10).

9.7 The balanced dataset

On the balanced dataset every negative is the fixed version of a vulnerable function, so there are no easy cases. The same method reaches a test ROC AUC of {{R_BAL_ROC}} here (95% interval {{R_BAL_CI}}). The interval includes 0.5, so I cannot say the model does better than chance. The paper reports 0.66 for ContraBERT and 0.69 for WizardCoder, and I did not reach their number. Likely reasons: ContraBERT is a stronger relative of CodeBERT, the paper tuned its settings on this dataset while I used standard ones, and the training split has only {{D_BAL_TRAIN}} functions. TF-IDF reaches {{R_BAL_TF}}, also close to chance. The F1 of {{R_BAL_F1}} in Table 12 looks good but means little: the best-F1 threshold flags almost every function, and flagging all of them already gives an F1 of {{R_BAL_F1_ALL}} on this split.

This is section 9.4 again from another side. Telling a vulnerable function from its own fix is the real task, and none of my models can do it.

9.8 Primary method against the alternative

The alternative freezes CodeBERT and trains only {{ALT_PARAMS}} numbers. It took {{R_ALT_MIN}} minutes in total, almost all of it one pass of CodeBERT over the data, against {{R_P_MIN}} minutes for the primary method. It is clearly worse: ROC AUC {{R_ALT_ROC}} against {{R_P_ROC}} and F1 {{R_ALT_F1}} against {{R_P_F1}}, both clear differences in Table 9. At a 10% review budget it finds {{R_ALT_BUDGET_10}} of the vulnerable functions, no more than the length-only model. The frozen vectors hold little that a linear model can use for this task; the fine-tuning is where the primary method gets its edge.

{{T_COST}}

For an organization the choice depends on what it can run and explain. With a GPU, fine-tuning takes about an hour and gives a model that orders the review queue well. Without one, TF-IDF gives the same ranking quality in {{R_TF_SEC}} seconds on a normal CPU, and its decisions are easier to explain, because each word has a weight. The frozen alternative is the weakest choice: it still needs CodeBERT and a GPU for the vectors, and it ranks no better than code length.

10. Recommendations

These follow from the numbers above and are written for a team that wants to use such a model on its own Java code.

  1. Use the model to order the review queue, never to approve code. Reading the top 10% of functions finds about half of the vulnerable ones; the other half is missed. A function the model does not flag is not safe.
  2. Measure recall at a review budget, not accuracy. At one vulnerable function in 35, accuracy rewards flagging nothing. Agree on how many functions the team can read, and report how many real vulnerabilities that finds. Check the threshold again on the team's own code, because it shifts between sets of commits ({{R_VALID_FLAG}} against {{R_TEST_FLAG}} flagged at the same threshold).
  3. Fix the data before buying a bigger model. The high scores come from the easy negatives, and on this data the paper's 13-billion-parameter model gained only about 0.01 ROC AUC over the CodeBERT-style ContraBERT. Better data would help more: a split by project, expert review of the {{D_QUARANTINED}} quarantined rows and of noisy labels, and a way to read functions longer than 512 tokens.
  4. Pick the cheapest method that is good enough. On this data TF-IDF ranked functions as well as fine-tuned CodeBERT, in seconds on a CPU instead of about 50 minutes on a GPU. The frozen alternative saves time but ranks no better than code length. A bigger model pays off only once the data is good enough for its extra capacity to matter.
  5. Do not add class weights by default; tune the threshold instead. In my runs the weights only moved where 0.5 falls and made the probabilities less reliable. Training without weights and choosing the threshold for the team's review budget was at least as good (F1 {{R_PL_F1}} against {{R_P_F1}}), and a threshold can be changed later without retraining.

11. Limitations

  • One run per setting. Each CodeBERT setting was trained once, with one seed. Training on the MPS GPU is not bit-for-bit repeatable, so a second run would give slightly different numbers. The bootstrap intervals cover the noise from the small test split, not the noise from training. A difference between two runs that is smaller than these intervals should not be read as real.
  • No split by project. The dataset has no project field, so the split is by commit, as in the paper. Code from the same project can sit in training and in test. On a project the model has never seen, the scores would most likely be lower. The paper names the same threat.
  • Code is cut at 512 tokens. About half of the vulnerable functions are longer, so the model sees only their beginning. The paper found that a longer context did not help its model on the balanced set, but I did not test this for CodeBERT.
  • Labels come from a rule. Nobody checked the labels by hand. The 41 quarantined rows are only the conflicts I could detect; wrong labels without a conflicting copy stay in the data.
  • Not the paper's exact test set. The published test file has {{D_TEST_FILE}} rows while the paper reports {{D_TEST_PAPER}}, and my cleaning removed {{D_TEST_REMOVED}} more. I compare my scores with the numbers printed in the paper; I did not re-run ContraBERT or WizardCoder.
  • Few hyperparameters tried. I used common CodeBERT settings and did not tune them, because one run takes about an hour on my laptop. The paper tuned its models. All three CodeBERT runs on X1 with P3 had their best validation score in the last of their four epochs, so longer training might help a little.
